# 待付款挂单延期（待部署）

2026-10-18需求：客户待付款时最多延期两次，从建单起最长挂单60天，期限到仍未付款则作废。

## 已实现（本地，待部署）
- 初始待付款期限沿用现有自动取消规则24小时；前端挂单倒计时使用后端权威期限，取代待付款阶段的15分钟显示。出货、安装延期保留。
- 每单最多2次；只允许期限内、状态pending_payment且payment_status=unpaid，且没有收款记录或HitPay成功记录的订单。第二次延期后仍保留至新期限到期，不立即作废。
- 员工填写每次延长的整数天数，延期从原截止时间累加，但不得超过created_at+60天。理由必填，记录操作人、原因、次数和新期限；前端防重复提交，数据库锁保证次数原子递增。
- 同门店店员/店长、同区域经理、全局管理层可操作；后端独立核验，不信任前端。权威次数和期限存在独立受保护表，客户端无直接写权。
- 自动过期每5分钟处理，保留订单及日志，不再执行旧函数的15天物理删除逻辑。收款记录写入使用同一订单行锁；过期前再次核验收款记录和支付状态。
- 已付款、部分付款、有收款记录及支付成功标记均不自动作废；支付平台尚未回传的支付仍需正常对账机制处理。

## 尚未确定与部署条件
- 用户已确认最长60天，按从建单起的总期限上限执行；不是每次延期60天。迁移执行时启用政策，但目前尚未部署到生产。
- 迁移在Supabase执行；已将max_hold_days=60作为服务器硬限制。仅发布HTML无法启用。
- 对现存待付款单初始化期限为created_at+24小时，与原24小时取消规则一致。启用前应审核历史待付款单；不能直接执行过期函数作为测试。
- 迁移替换旧定时任务；不要在本迁移之后重新运行旧auto_expire_unpaid_orders_migration.sql，否则会恢复旧规则。
- 已通过JS语法、按钮状态、后端静态规则和临时PGlite PostgreSQL/PLpgSQL执行验证：初始24小时、第三次延期被拒绝、60天上限、跨门店拒绝、空原因、已收款保护、过期作废不删档和重复任务幂等。pg_cron登记及多连接并发仍需测试环境验证。

## 手动操作原则（用户补充确认）
- 延期仅由员工主动点击、填写天数和必填原因并确认后调用RPC；后台任务绝不自动延长。
- 原因全空格或超过500字前后端均拒绝；取消弹窗不消耗次数、不修改截止时间。
- 未操作延期仍按原建单24小时未付款自动取消；延期后按新期限执行。最多2次是可用次数，不是自动赠送的保留期；60天是总上限，不是默认挂单时长。
