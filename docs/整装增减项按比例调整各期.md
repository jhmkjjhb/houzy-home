# 整装增减项按比例调整各期

客户签署增项或减项后，期数不变，已付清的期数不变；增减金额按原合同比例分到还没付清的各期。每期按整数马币调整，零头放在最后一期，所以各期加起来永远等于项目当前总额。

例：合同 RM100,000，四期 30% / 30% / 30% / 10%，前两期已付清。
- 签减项 RM4,000：第 3 期 30,000 → 27,000，第 4 期 10,000 → 9,000。
- 再签增项 RM8,000：第 3 期 → 33,000，第 4 期 → 11,000。

## 客户看到什么
- 签增项、减项前，签署页显示「签署后，您的付款计划会这样调整」对照表：每期原应付、签署后应付、变化，以及合计。签名即确认新的各期金额；对照表存进签署记录。
- 客户付款页和每期付款单 PDF：金额变过的期数注明「原合同本期 RM…，因已签增减项按比例调整为 RM…」。
- 家人代签链接沿用原来的做法，不显示金额总额，也不显示付款计划。
- 增项、减项签署链接打开后先要输入业主登记手机号后四位，验证通过才显示内容和签名框（`supabase/renovation_signing_phone_check_migration.sql`）。输错 8 次锁 1 小时；验证后 30 分钟内可签。链接被转到群里，别人也看不到金额、签不了名。业主自己的项目页面不变。

## 特殊情况
- 某期已付一部分：新金额不低于已付金额，不够减的部分转到其他未付清的期数。
- 原合同各期都已付清：新增项照旧单独成一个付款节点，按员工填写的付款节点收款。
- 减项超过所有未付清金额：门店登记时就会拒绝，和以前一样。
- 已签增项由店长作废：金额按同样比例从未付清的各期退回。

## 不改的
- 本次上线前已签、单独挂着的增项，保持单独付款节点。
- 本次上线前已签的减项（当时从最后一期往前扣），金额保持不变。
- 原合同和合同 PDF 保留签约时的原始分期。

## 上线顺序
1. 在 Supabase SQL Editor 执行 `supabase/renovation_prorate_installments_migration.sql`（需在所有整装迁移之后，包括部分减项、分期付款单和付款单联系电话）。可重复执行。
2. 推送前端：`portal/renovation/finance-view.js`、`addition-signing.js`、`deduction-signing.js`、`additions.js`、`installment-statement.js`、`customer-workspace.css`。前端在数据库更新前上线也不会出错，只是还不显示对照表。
3. 用测试项目核对：签一张减项、一张增项，看签署页对照表、客户付款页金额和付款单 PDF。

## 测试
`tests/renovation-prorate-installments.mjs`（30 项）：按比例分摊、已付清不变、零头放最后一期、部分付款不被减到已付以下、增项作废退回、各期合计等于项目总额、旧增项不变、全部付清时增项单独计费、代签链接不显示计划。
